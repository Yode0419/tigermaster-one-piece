# 分流與優先級規則

來源：`docs/exploration/in-progress/priority-review/priority-criteria.md`、`defect-severity.md`（兩者皆為草稿）。改規則時兩邊一起改。

## 分流：需求還是 Bug？

遇到的人會覺得「怎麼會這樣？」→ Bug；覺得「如果有這個就好了」→ 需求。

例：按「送出」沒反應，是 Bug；想在送出前多一個確認視窗，是需求。

## 需求票優先級：四題加總

每題 1 到 3 分，一次問一題：

1. **使用者體感**：受影響的人覺得痛、而且常發生嗎？（3 痛且高頻／2 有感但可忍或低頻／1 幾乎無感或有替代方案）
2. **內部人力成本**：目前要花內部多少時間處理？（3 每週或每案都要／2 偶爾／1 幾乎不用）
3. **產品策略相關性**：呼應目前實際在推的方向嗎？（3 已有共識且正在投入／2 呼應大方向但非焦點／1 無關）
4. **風險降低價值**：不做的話容易出錯、後果嚴重嗎？（3 容易出錯且嚴重、沒有機制擋／2 偶爾、可控／1 幾乎不會）

加總 4 到 12：**≥10 High｜7～9 Medium｜≤6 Low**

- 分數只是輔助。跟直覺明顯不符時可以覆寫，但要說理由。
- 不評工程量，不用營收或轉換率當主要理由，三種角色均衡看待。
- 牽涉金流不代表風險自動判高，要看目前的補救措施是否脆弱。
- 業務決策還沒定案（要不要做、規則怎麼訂）時，不硬評分，建議先不設優先級。

## Bug 票

不評嚴重度（SCRUM 的「漏洞」類型無法設定優先級）。
