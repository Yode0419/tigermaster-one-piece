# 後台操作指南建置方法論

_起頭文件，記錄為什麼要做這件事、現況盤點結果，以及文件規格。方法論定案後由 `/robin` 同步進永久知識層。實際的操作指南內容不放在本資料夾，直接建置在 `docs/wiki/operations/backoffice-guide/`，漸進式發布。_

_最後更新：2026-09-17_

---

## 緣起

公司顧問提出的建議，具體痛點：

- 新人(含顧問自己)拿到後台帳號但沒人帶，怕亂點壞東西
- 客服目前靠資深客服口頭訓練，沒有書面文件，知識鎖在特定人身上
- 策略層考量：公司若未來增資或被併購，盡職調查會檢視知識是否文件化，不依賴特定人員

## 現況盤點

- 後台相關知識目前散落在 34 個既有 wiki／exploration 文件裡，依業務功能組織(而非依系統介面)，已覆蓋：訂單管理、訂單財務、服務分類、折價券、積分系統、用戶反饋、招募活動
- 完全沒有文件覆蓋的模組：廣播通知、廣告管理、徽章圖示、新聞資訊、獎勵推薦、精選文章、登入記錄、假期管理
- 後台前端 repo：`C:\Users\yode0\develop\source_code\fdtigermaster-admin-web`，Vue2，約 18-20 個功能模組、46 條路由、71 個 .vue 檔案。自身 README 只寫技術架構，沒有業務操作內容
- 後端 repo：`fdtigermaster-functions`(Firebase Functions，約近千檔案，`src/ApiEntries/` 底下的 API 分類名稱與後台模組高度對應，例如 CouponApi、NewsApi、BadgeApi、SelectedArticleApi，可用來輔助判斷風險等級)、`fdtigermaster-experience-db`(Java/Spring Boot 獨立服務，處理 Membership／Plan／VoucherWallet／RefundRequest 等，對應 Pro 會員與 Tiger Points 相關邏輯)。PM 不熟後端，這兩個是目前已知的，後端服務主要跑在 GCP，實際數量可能不只這兩個，尚未確認是否還有遺漏

## 方向決定

不做一份獨立大手冊，改採：

1. 先建 overview.md 讓讀者有整體輪廓，已知高風險頁面標 ⚠，解決「不敢亂點」的立即痛點
2. 依優先序(客服常用頁面優先)逐一補頁面說明，漸進式發布，不等全部完成
3. 維護掛在既有後台改版流程裡，功能改版時順便更新對應頁面，不另排期抽查

## 用詞

- 後台側邊欄的每一項，統一稱「頁面」，不稱「模組」：「模組」是工程用語，「頁面」比較貼近客服／新人實際描述後台的方式，也對應到畫面本身
- 兩種內容文件類型稱「功能說明文件」與「操作指南文件」

## 內容風格

- 程式碼掃描只是**驗證手段**，不是要保留的內容。正文一律用白話寫「查證後的結論」，不寫檔名、file:line、API／函式名稱、程式碼片段
- 查證中發現的技術現況(例如某功能其實還沒做完)要轉譯成白話講清楚現況跟影響，一樣不附程式碼佐證，但要如實呈現，不要因為怕技術感就把真實現況隱藏或淡化
- 篇幅視頁面複雜度而定：單純瀏覽用的頁面可以幾行帶過，複雜頁面才需要完整寫，整體偏好精簡寫重點，不要為了格式完整硬湊內容
- 參考基準：`docs/wiki/product/coupon-system.md` 的調性(概述、表格化欄位說明、條列流程，完全沒有程式碼痕跡)

## 文件規格

五種文件角色分開，各自單純：

**INDEX.md**(`docs/wiki/operations/backoffice-guide/INDEX.md`)：純目錄，跟 repo 裡其他 INDEX.md(例如 `docs/wiki/INDEX.md`)同樣風格，一行一份文件加一句話描述，不放資料表。分兩區：「功能說明」「操作指南」，各自列出已經寫好的文件

**overview.md**(`docs/wiki/operations/backoffice-guide/overview.md`)：讀者的第一份文件，目的是建立後台系統的整體輪廓與心智模型，不是逐頁清單。依現有側邊欄分類分組(例如訂單管理、會員管理)，每組一小段白話描述在幹嘛、列出包含哪些頁面、連結到已寫好的功能說明文件。已知有不可逆／高風險操作的頁面，在頁面名稱旁加 ⚠，不另外列風險等級欄位或表格，風險細節交給該頁功能說明文件的「需要注意的地方」。複雜頁面群(見下方「巢狀頁面處理規則」)在這裡只列頁面群名稱＋一句話描述，不展開逐分頁清單

**build-tracker.md**(`docs/exploration/in-progress/backoffice-guide/build-tracker.md`，PM 自己用，不對外)：真正的建置進度追蹤表，逐頁(複雜頁面群展開後含每個分頁)列出風險等級(低／中／高／不確定，只填一個詞，理由寫進功能說明文件裡)、說明文件是否已寫(有則連結，無則標「尚無」)、對應 wiki 業務文件。新開的 session 看這張表就知道做到哪、下一個該做哪個。這張表原本是 overview.md 的內容，因為讀者導覽跟建置追蹤是兩種不同需求而分開

**功能說明文件**(`docs/wiki/operations/backoffice-guide/<slug>.md`，每個後台頁面一份，漸進式增加)：只回答「這是什麼」，不寫操作步驟。固定 4 欄：

1. 這是什麼(一句話帶到誰會用到，不獨立開欄位)
2. 功能內容(能力清單，列點分述，不是操作步驟)
3. 需要注意的地方(白話講風險與可逆性；標題可依頁面實際狀態替換，例如未上線頁面用「目前狀況」，但頁面已有實質功能時標題固定用「需要注意的地方」)
4. 相關連結(業務規則連結既有 wiki 文件；操作指南現階段一律寫「尚無，待累積」)

全程不寫程式碼引註，篇幅視頁面複雜度而定，簡單頁面幾行帶過即可。範本參考 `docs/wiki/product/coupon-system.md` 的調性。屬於巢狀頁面群(清單→詳情→多分頁)的頁面，欄位規則見下方「巢狀頁面處理規則」

**操作指南文件**(`docs/wiki/operations/backoffice-guide/procedures/<slug>.md`，現階段不建置)：回答「怎麼把一件事做完」，範圍可以是單一頁面內的操作，也可以是跨頁面的業務情境，兩者用同一種文件處理。內容連結回相關的功能說明文件，不重複寫「這是什麼」

風險提醒(可逆／不可逆)放在功能說明文件的「需要注意的地方」，不是操作指南才講，因為這不需要等實際操作情境確認，靠掃程式碼就能先給結論，直接回應「怕亂點壞東西」的訴求。

功能說明文件與操作指南之間是雙向連結，但**手動維護，不是自動 backlink**：操作指南文件連到相關的功能說明文件；等操作指南寫出來後，也要回頭在它用到的功能說明文件裡補上連結。這是純 Markdown，不是 Obsidian，沒有自動掃描機制。

## 巢狀頁面處理規則

後台不少入口不是單一畫面，而是「清單→詳情→多分頁」的結構，例如訂單詳情(進行中訂單／已完成訂單點進去後，9 個分頁：基本資料、符合工項照片、施工照片、訂單註記、報價單、訂單評論、付款紀錄、訂單紀錄、聊天室)。已知還有使用者詳情、說明會等頁面也是同樣結構。這是**通用規則，不是個案處理**：

- 清單頁(例如「進行中訂單」「已完成訂單」)各自維持一份精簡的功能說明文件，只講清單本身的搜尋／篩選／欄位顯示，不重複詳情頁內容
- 詳情頁若有分頁結構，整個視為一個「複雜頁面群」，開一個資料夾，資料夾名稱用頁面名稱(例如 `docs/wiki/operations/backoffice-guide/訂單詳情/`)，底下放各分頁檔案(例如 `基本資料.md`、`報價單.md`、`付款紀錄.md`)
- 不另開 README／總覽檔案。overview.md 只列頁面群名稱與一句話描述(給讀者導覽用)；逐分頁的風險等級與建置狀態記在 build-tracker.md(給 PM 建置追蹤用)
- 每份分頁檔案開頭標明「所屬頁面：OOO」，讓讀者(人或 AI)知道自己在哪個複雜頁面群底下
- 清單頁的功能說明文件用連結指向對應的複雜頁面群資料夾，不重複寫詳情頁內容
- 分頁如果內容很薄，可以合併成一份檔案(例如把「訂單旗標」「訂單費用」兩個小分頁合併成「訂單旗標與費用.md」)，不用每個 UI 分頁都硬開一份文件
- 「有哪些欄位可以編輯」屬於功能內容欄位(靜態盤點能力)；「什麼情境下該編輯、為什麼」屬於操作指南(業務判斷)，這條分界線同樣適用於複雜頁面群底下的每份分頁檔案

完整的巢狀頁面清單，等實際逐頁盤點 build-tracker.md 時才會確定，目前先記錄已知案例。

## 逐頁面建置流程(SOP)

**功能說明文件**(可多個頁面一起做)：

1. 打開 `build-tracker.md`，挑「說明文件」欄位空白的頁面
2. 用 scout 掃描該頁面對應的前端路由([[reference_admin_web_codebase_path]])與後端 API([[reference_backend_repos_path]])，列出實際有哪些操作(新增／編輯／刪除／查詢)，並判斷風險等級與可逆性；同時判斷這個頁面是不是「清單→詳情→多分頁」的複雜頁面群，是的話走資料夾規則。掃描工作外包給 scout，不在主對話裡直接讀整包程式碼(尤其 `fdtigermaster-functions` 近千個檔案)
3. 對照既有 34 份 wiki／exploration 文件，找出這個頁面對應的業務規則文件
4. 把查證結果轉譯成白話寫成功能說明文件，**不保留程式碼引註**；更新 `build-tracker.md` 的「說明文件」欄位，並在 `INDEX.md` 補上一行；如果該頁面所屬的分類還沒被列進 `overview.md`，一併補上一小段描述
5. Commit，可以多個頁面一起做完再一次 commit，也可以一個一個做，視當次工作量而定

**操作指南文件**(現階段不建置，先記錄未來怎麼做)：

- 等 PM 實際知道有哪些值得寫的操作或情境(不用等全部頁面都有說明文件才開始)，一個一個寫，依 PM 對客服實際使用頻率的判斷排序
- PM 依自己熟悉程度直接寫操作內容；不確定或懷疑客服有特殊固定流程的地方標記「待確認」，找適當時機(例如順便問一句)跟客服確認即可，不用為此特別排訪談
- 有牽涉「是否可逆」這類需要程式碼驗證的細節，用 scout 對照程式碼確認，不能只憑印象寫，但寫進文件時只留白話結論
- 完成後在 `INDEX.md` 的「操作指南」區塊補上一行，並回頭在相關的功能說明文件補上連結

新的 session 只要讀這份方法論文件＋打開 `build-tracker.md`，就能接續進度，不依賴對話記憶。

## 儲存架構

- 圖片(截圖)放在 `docs/wiki/operations/backoffice-guide/assets/` 單一共用資料夾，整份操作手冊共用，不是每個頁面／複雜頁面群各自開 assets，方便未來如果要把整份手冊搬離這個知識庫。存放模式比照 `exploration/completed/website-optimization` 的 assets 資料夾
- 影片不進 git：目前使用個人免費 GitHub，單一檔案超過 100MB 無法直接 push，螢幕錄影容易超過此限制。影片放外部平台，md 內僅放連結加說明
- 外部平台選型(Google Drive／Notion)先不定案，等真的有影片需求時再選

## 待討論／未定案事項

- 客服／顧問等非工程背景讀者實際會怎麼存取這份指南(GitHub 網頁／其他工具)，待與顧問、董事長一起討論，會影響知識庫未來是否要開放給更多角色，範圍比本專案大，不卡在這裡處理
- 後端服務是否還有遺漏未列出的 repo(目前主要靠 GCP，PM 不熟後端全貌)，如果之後發現有其他服務，補進「現況盤點」
- `procedures/` 資料夾的實體命名要不要跟著改名(層級已改稱「操作指南」)，例如改成 `guides/`
- 完整的巢狀頁面(清單→詳情→多分頁)清單，目前只知道訂單詳情、使用者詳情、說明會，等逐頁盤點 build-tracker.md 時才會確定
