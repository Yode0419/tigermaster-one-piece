# B2B2C 串接專案：決策記錄

一行一則，記錄討論中定下的決定。

- 2026-10-07: 資料夾 `web-ordering/` 改名為 `b2b2c-integration/`，原構想文件留作前身。Why: 董事長說 Web 和企業串接是同一件事。
- 2026-10-07: 聊天納入第一版設計範圍，方向是用專屬連結進入的網頁訂單頁（狀態、聊天）。Why: 董事長認為「找得到師傅」和收單同等必要，且合作企業不必自行開發聊天。
- 2026-10-07: 付款初期以 App 內為主，網頁訂單頁只顯示狀態與聊天並引導到 App。Why: 沿用既有付款流程。
- 2026-10-07: 是否收派遣費、付款時限長短，依合作企業個別設定，細節帶到 10/14 會議。Why: 每家企業的商業條件不同。
- 2026-10-07: 預建帳號的認領方式之後再設計，前提是第一版不改 App 程式碼。Why: 簡訊驗證目前關閉，且不動 App 是本專案限制。
- 2026-10-07: 通知只用 Email 與網頁訂單頁，不討論重啟簡訊或 LINE 官方帳號推播。Why: 公司目前沒有發簡訊，避免範圍發散。
- 2026-10-07: 企業串接不需註冊或登入，有帳號就直接成立訂單，沒有就預建帳號再成立訂單。Why: 資料由合作企業直接送來。
- 2026-10-07: 師虎 Web 走接近 App 的流程，消費者在網頁自行註冊並設定密碼，不預建帳號；身分流程（先登入或 SCRUM-35 延後登入）設計時再定。Why: 師虎 Web 是自家前端，可以有完整體驗。
- 2026-10-07: 師虎 Web 下單表單 = 收單 API 欄位 + App 既有體驗（派遣費說明與同意、預約或立即、加成提醒、電梯、照片、確認頁），不做發票與優惠。Why: 付款在 App，發票可付款前補填；優惠之後視需求補。
- 2026-10-07: 企業設定（名稱、訂單代碼、派遣費、付款時限、預設服務時段）第一版由工程師寫死，後台只顯示訂單來源；管理頁列為後續。Why: 第一版只有兩個來源。
- 2026-10-07: backlog 只放設計端工作，之後轉 Jira；給合作企業的文件與後續優化先記在 overview，不列入 backlog。Why: 本資料夾是設計工作。
- 2026-10-08: 流程與功能設計要同時涵蓋「要付派遣費」與「不用付」兩種訂單，可依企業個別設定；智生活實際採哪一種等洽談結果。Why: 董事長無法直接回答，要看與智生活談的結果。
- 2026-10-08: 加成規則提供給合作企業，由他們決定靜態展示或在自家 App 自動提醒；我方只接收服務時間，不回傳是否落在加成時段。Why: 10/07 會議已談定，減少串接來回。
- 2026-10-08: 網頁聊天會開放給消費者使用，入口與流程待設計。Why: 技術上可行，剩下是設計題。
- 2026-10-08: 收單 API 的照片為選填欄位。Why: 不強迫合作企業收集照片。
- 2026-10-08: 訂單編號的每日流水號全站共用，不依來源分開計數。Why: 簡報寫法，PM 確認。
- 2026-10-08: 條款同意由合作企業的合約涵蓋，不回傳消費者同意時間。Why: 簡化串接。
- 2026-10-08: 待確認問題只問影響方案方向的事，連結期限、聊天嵌入方式、Email 提醒條件等細節等方案定了再談。Why: 方案未定就談細節會失焦。
- 2026-10-08: 網頁訂單頁不另外定付款相關的狀態名稱，付款全部走 App 既有流程與名稱，簡報的「待付款」不需統一。Why: 董事長說付款都走原本 App。
- 2026-10-08: 服務時間希望由合作企業提供，依該時間媒合，與 App 預約叫修相同；沒提供時由系統自動帶入預設時間去媒合，預設時間可依企業個別設定（沿用 10/07 企業設定中的預設服務時段）。Why: 消費者不一定給得出時間，類似 App 立即叫修預設 2 小時。
- 2026-10-08: 來源資料（簡報 PDF、會議逐字稿、前身構想）收進 `sources/`，根目錄只留 overview、backlog、decisions、open-questions；逐字稿改英文檔名，PDF 保留原檔名。Why: backlog 開工後檔案會變多，工作文件和來源資料要分開。
