# SCRUM 票優先順序評估

> 用途：快速判斷一張 SCRUM 票的優先順序（High／Medium／Low）。只評「想要的新功能或改善」；已經壞掉的票不用這套分數，另外看 [缺陷嚴重度判斷](defect-severity.md)。狀態：草稿，待確認。

## 回答四題，加總看分數

### 1. 使用者體感

受影響的人會覺得這個問題很痛、而且常常發生嗎？

- 高（3分）：痛點明顯，且高頻發生
- 中（2分）：有感但可忍受，或低頻
- 低（1分）：幾乎無感，或有替代方案

### 2. 內部人力成本

這件事目前每次／每週要花內部多少時間處理？

- 高（3分）：經常性（每週／每案）都要花時間處理
- 中（2分）：偶爾需要處理，頻率不高
- 低（1分）：幾乎不需要額外花時間

### 3. 產品策略相關性

這件事呼應目前實際在推的方向嗎？

- 高（3分）：已有明確共識、正在投入的方向
- 中（2分）：呼應大方向但非當前焦點
- 低（1分）：與現階段策略無關

### 4. 風險降低價值

這件事如果一直不做，會不會真的出過代價高的錯、或很容易出錯？

- 高（3分）：容易出錯、後果嚴重，現在沒有機制擋
- 中（2分）：偶爾可能出錯，但後果可控
- 低（1分）：幾乎不會出錯，或出錯也沒什麼影響

## 對照分數

四題加總（範圍 4～12）：

- **≥10 → High**
- **7～9 → Medium**
- **≤6 → Low**

這是輔助工具，不是聖旨。分數跟直覺明顯不符時，直接覆寫並註明理由。

## 備註

- 工程量級不在這裡評估，交給團隊的 story point 流程處理。
- 三種角色（客戶／師傅／內部客服會計）均衡看待，不用「營收／轉換率」當主要理由。
- 風險降低價值不因牽涉金流就自動判高，要看補救措施本身是否脆弱、容易出錯。
- 票擺放很久不直接加分，只當作重新檢視舊評估理由是否還站得住腳的信號。
- 少數票有明確時間壓力或證據薄弱，用文字標籤（⏰／❓）標注即可，不做成正式評分題。
- 票本身牽涉的業務決策還沒定案（例如某個功能要不要做、規則怎麼訂）時，標「待討論」，不硬塞分數。
