# SCRUM 票缺陷（Bug）嚴重度判斷

> 用途：判斷系統行為跟設計不符、已經壞掉的票該多急處理。不跟功能票用同一套分數比重要性，理論上都該修，差別只在先後順序。為什麼要分開判斷，見 [priority-criteria.md](priority-criteria.md)。狀態：草稿，待確認。

## 判斷測試：這算不算 bug？

問的不是「這個能力有沒有寫進程式碼」，是「系統現在的行為，有沒有違反一個照理說應該成立的規則」：

- **違反了 → bug**。例：票裡寫著某個狀態「理論上不應該」發生（例如已結案的東西不應該再被更動），系統卻沒擋下來——這個「不應該」是業務邏輯早就該保證的事，即使這個防呆機制從來沒被實作過，也算 bug，不算功能請求。
- **沒有違反，只是想要一個目前不存在、也沒人預期系統會自動處理的新能力 → 功能請求**，不算 bug。例：後台想新增一個原本沒有的操作工具——沒有人預期這個工具本來就該存在，這純粹是想要新增能力。

## 兩級嚴重度

- **高**：已造成實際事故，或會讓流程卡死
- **低**：純視覺／動畫瑕疵，不影響核心功能
