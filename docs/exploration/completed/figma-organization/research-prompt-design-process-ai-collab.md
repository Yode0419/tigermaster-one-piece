# 研究提示詞：設計流程／交付開發／設計檔案維護／AI協作（中小企業適用）

用途：這是一份要拿去新 session（或其他研究工具）使用的研究提示詞，不是研究結果本身。
背景脈絡（公司規模、現況）已寫入提示詞內，新 session 不需要額外解釋即可直接使用。

---

```
我是一間中小企業的 UIUX 設計師（家庭修繕媒合平台，公司規模小，目前只有我一位設計師，
沒有獨立的 UX Ops／DesignOps 職位，開發端也是小型團隊而非分工細緻的大型工程組織）。
目前用 Figma 作為設計工具，並已開始嘗試用 AI（LLM agent，透過類似 MCP 的方式連接
設計工具）輔助部分工作。

我要研究「設計流程」「交付開發」「設計檔案維護」「AI 協作」這四個主題的成熟方法論，
目的是建立一套適合中小企業規模、但保留擴張彈性的工作方式——不是抄大型企業的
DesignOps 框架（那通常假設有專職角色、多個團隊分工），但也不要是「因陋就簡」的
權宜之計，而是有紮實道理、之後團隊變大也不用整套打掉重練的做法。

請針對以下四個主題分別研究：

1. 設計流程（Design Process）
   - 從發想到定稿到交付的完整流程，特別是「沒有專職 DesignOps、一人或極小型設計團隊」
     情境下的簡化版本，核心步驟不能省略哪些、可以省略哪些
   - 探索期／收斂期／交付期各階段應該用什麼工具或做法區分（不限於特定廠商工具）

2. 交付開發（Design-to-Dev Handoff）
   - 沒有正式 handoff 流程與大型工程團隊時，設計與開發怎麼維持同步、避免「設計稿
     跟實際上線的產品長期漂移」
   - 交付的定義該怎麼認定（設計完成＝真的會被開發嗎？如何避免兩邊各自認知不同步）

3. 設計檔案維護（Design File / Asset Maintenance）
   - 檔案／專案的生命週期管理：從草稿、進行中、交付、上線後封存，業界成熟的做法
   - 命名與狀態標記慣例、主檔案與版本管理的取捨（例如分支 vs. 獨立檔案兩種模式的
     適用情境）
   - 這套做法在團隊從 1 人成長到多人時，哪些部分會需要調整、哪些部分是打地基不用重做

4. AI 協作（AI Collaboration in Design Work）
   - 目前 AI／LLM agent 在設計工作流程中，有紮實文件記載（不是廠商行銷宣稱）的協作
     模式有哪些：包含但不限於設計系統一致性稽核、交付前檢查、文件與知識庫同步
   - 哪些是「不管換哪個工具或哪個 AI 廠商都成立」的核心協作原則，哪些是特定工具
     （如特定設計軟體的特定外掛／MCP server）綁定、換工具就會失效的做法
   - 中小企業／小型設計團隊實際導入 AI 協作時，常見的落地方式跟常見的坑

研究限制與要求：
- 避免過時資料：AI 協作與設計工具生態變化很快，請優先找近 1-2 年內的資料，
  引用較舊的資料（尤其 AI 相關）時要明確標註年份，不要當作當前最佳實踐引用
- 方法論優先於工具操作細節：我要的是「為什麼這樣做、背後的原則是什麼」，
  不是特定軟體的按鍵教學——目的是即使日後更換工具，這套邏輯依然適用
- 明確區分「有文件根據的成熟做法」跟「廠商行銷話術／未驗證宣稱」，兩者都要
  引用來源，但清楚標註可信度等級
- 優先參考多個獨立來源交叉印證的做法，而非單一廠商的一面之詞
- 特別標註哪些做法是「大型企業框架直接搬過來，中小企業不適用或需要大幅簡化」，
  哪些是「規模無關、從一人到百人都成立的核心原則」

請提供：每個主題的直接結論 → 支持的證據與來源（含日期）→ 中小企業適用性的取捨判斷
→ 尚未找到明確答案或有爭議的地方要明講，不要用推測填補。
```

## 背景

此提示詞是在 tigermaster-one-piece 專案 Figma 檔案整理討論過程中產出（見
[figma-folder-architecture-decision.md](figma-folder-architecture-decision.md)）。當時已針對 Figma
資料夾組織模式與 AI／Figma MCP 協作現況做過一輪研究，此提示詞是延伸——把範圍從
「Figma 這個工具」擴大到「設計流程、交付開發、檔案維護、AI 協作」的通用方法論，
刻意要求不綁定特定工具，因為設計師希望這套邏輯換工具後依然適用。
